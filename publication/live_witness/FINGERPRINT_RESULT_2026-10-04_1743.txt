[7] WHAT THIS MEANS
    The camera's sshd answered, but with a DIFFERENT host key than the one inside
    BODYDATA.DAT. The reason is visible in the firmware itself: that key lives at
    /tmp_network/ssh/ssh_host_ecdsa_key and is created on demand by
    /usr/bin/create_host_key.sh (ssh-keygen -q -b 256 -t ecdsa -N '' -f ...) only if
    the file is not there already. A key under /tmp_network does not survive a
    reboot, so a camera that rebuilds it shows a fresh key while still carrying the
    same script and the same bytes in the firmware file.
    This is the strong form of that finding, not a coincidence of another device:
    the server that answered negotiated EXACTLY the algorithm set the firmware's
    sshd_config imposes (ecdh-sha2-nistp256 / aes128-ctr / hmac-sha2-256 / ecdsa-sha2-nistp256) - a set no
    ordinary machine chooses. So the firmware's sshd IS running, and its host key
    file was regenerated on the device: the private key shipped inside the public
    firmware image is not the live identity of this camera.
    What is measured on 2026-10-04: the camera at 192.168.1.102 presented
      SHA256:0VOxJqn75lys4Lf91tSlZu8nazWWxD6rTVc35jZo87U

    templates that were never a persisted identity. If the fingerprint stays the
